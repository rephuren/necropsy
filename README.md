# necropsy

Вскрытие бинарников: свой разборщик ELF и PE на Go без внешних зависимостей, паттерны ImHex, учебные программы на x86-64 assembly и решения на pwntools. Работа только с собственными учебными бинарниками и файлами, которые вы вправе исследовать.

Статус: ранняя версия. Готов разбор ELF и PE; учебные бинарники и паттерны ImHex в планах (см. [CHANGELOG](CHANGELOG.md)).

## Быстрый старт

```bash
go build -o bin/necropsy ./cmd/necropsy
bin/necropsy inspect ./некий-elf-файл          # заголовок, зависимости, защита, секции с энтропией
bin/necropsy inspect --json ./некий-elf-файл   # то же в JSON
bin/necropsy strings ./образец                # строки ASCII и UTF-16LE, только классифицированные (--all, --class url,ip, --json)
go test ./...
```

Формат определяется по началу файла. Что показывает `inspect` для ELF 32/64 (little-endian): архитектуру и тип, точку входа, интерпретатор и `DT_NEEDED`, RUNPATH, сегменты и секции с энтропией по Шеннону, а также сводку в духе checksec: PIE, NX, RELRO (none/partial/full), канарейка стека, `_chk`-функции (fortify), stripped, статическая линковка, сегменты RWX. Предупреждения: секция с энтропией выше 7,2 (упаковано или зашифровано?), исполняемый стек, RUNPATH. Сжатые секции `.debug_*` под это предупреждение не попадают.

Для PE32/PE32+: архитектуру, точку входа и секцию, где она лежит, ImageBase, подсистему, секции с энтропией и флагами, таблицу импорта (DLL и функции, включая импорт по ординалу), флаги защиты (ASLR, high-entropy VA, DEP, CFG, отсутствие SEH, подпись) и предупреждения: нет ASLR или DEP, секции RWX, точка входа вне `.text`, высокая энтропия.

`strings` достаёт строки ASCII и UTF-16LE с их смещениями и относит каждую к классу: `url`, `ip`, `email`, `path`, `registry`, `private-key`, `base64`, `api` (имена вызовов, частые при разборе вредоносов) или обычный текст. По умолчанию показываются только классифицированные строки. Само по себе присутствие API-имени ничего не доказывает: так делают и обычные программы.

## Как проверялось

- Разборщик написан с нуля, а стандартная `debug/elf` используется **только в тестах как эталон**: на реальных бинарниках Go для amd64, arm64 и 386 совпадают заголовок, все сегменты, все секции и число символов. Для PE то же самое с `debug/pe`: заголовки, секции (включая длинные имена из таблицы строк COFF) и полный список импортов для windows/amd64, 386 и arm64.
- Обрезанные и испорченные файлы (сотни вариантов) не вызывают паники и зависания. Все чтения идут с проверкой границ, числа из заголовков ограничены.
- `go vet` и тесты в CI.

## Ограничения

- Только little-endian ELF. Big-endian отклоняется с ошибкой.
- PE: нет разбора экспорта, ресурсов, отложенного импорта и сертификата (проверяется только его наличие). Эталон для PE тоже бинарники Go, а не файлы MSVC или MinGW.
- Оценка «канарейка» и «fortify» строится по именам символов, поэтому у stripped-файлов она может быть неточной.
- Сверка с эталоном шла на бинарниках Go; на файлах, собранных gcc/clang с динамической линковкой, проверено только на ручных заголовках, а не на реальном образце.
- Это учебный инструмент, он не заменяет `readelf`, `checksec` и Ghidra.
